## 3. 品质 = 价值 / 稀有度标签（**不是强度分级**）

> 用户 10:36 明确：*"我说的物品品质只是代表了这个物品的价值，这个游戏暂时没有刷子系统，不需要刷取不同等级不同稀有度不同强度的装备。（后续可能变动）"*

### 定义

| 品质**是**            | 品质**不是**               |
| ------------------ | ---------------------- |
| "这东西多贵重 / 多稀有"的标签  | 不是"强度分级"               |
| 用于 UI 边框颜色、掉落权重、排序 | 不决定伤害、治疗量、护甲值          |
| **同一种物品只有一个品质**    | 不存在"白 AK"和"紫 AK"两种同名装备 |

**因此本游戏没有"刷装"循环**：你捡到的 AK 就是 AK，价值由它的品质档位决定，不存在"刷一把更好的 AK"。

## 3.5 堆叠规则（**硬规则**，用户 10:36 定义）

> 原话：*"无论是背包、弹挂、仓库或者任何其他类似情况，物品只要没有明确最大堆叠数量，那么就不可堆叠，例如 2 把武器 AK47，虽然属性完全相同，但也不可以堆叠到一起。其他物品 item 同理。除非类似钞票等有写明堆叠数量=500，那么就可以堆叠最大 500 张。任何尝试将不可堆叠物品堆叠一起的物品都是非法行为，包括尝试把物品堆叠到武器上。"*

### 规则表

| 情况                     | 结果                       |
| ---------------------- | ------------------------ |
| `stackLimit` 没填 / = 1  | **不可堆叠**：每次拾取占一个**独立条目** |
| `stackLimit` = 500（钞票） | 可堆叠，最多 500               |
| 两把 AK47（属性完全相同）        | **不可堆叠**，两个独立条目，各占各自格子   |
| 试图合并不可堆叠物品             | **非法**，代码必须阻止            |
| 试图把物品"堆叠到武器上"          | **非法**                   |

### 实现要求（写进 7.1 的验收）

1. `stackLimit` **默认 1**（不是 0、不是 99）
2. 添加物品时：
   - `stackLimit <= 1` → **总是新增独立条目**
   - `stackLimit > 1` → 先找同 id 且未满的条目填充，满了再新增
3. `CanMerge(a, b)` 只有在 `同 id && stackLimit > 1 && a.count + b.count <= stackLimit` 时才为 true
4. **绝不允许**对 `stackLimit <= 1` 的条目执行合并 —— 开发期应 `Debug.Assert` 拦截
5. 武器槽一次一格，天然不接受堆叠

### 数据结构：必须用 `List<ItemStack>`

```csharp
// ✅ 正确：每个条目独立
List<ItemStack> {
  { "ak47",          count: 1 },     // 第一把 AK
  { "ak47",          count: 1 },     // 第二把 AK —— 独立条目
  { "money",         count: 500 },   // 钞票，可堆叠
  { "solar_panel",   count: 1 },     // 太阳能板，占 2×4
}

// ❌ 错误：Dictionary<id, count> 会把两把 AK 合成 count=2（非法）
Dictionary { "ak47": 2 }
```

**这是本期最重要的数据结构约束**：`count` 只是"这一条目里有几个"，不代表"同 id 的所有物品都在这儿"。

## 3.6 背包是二维网格（因为物品有尺寸）

用户例子：太阳能板 **2×4 = 8 格**。这说明背包**不是"N 个独立槽位"**，而是有宽高的网格。

| 概念               | 说明                                                      |
| ---------------- | ------------------------------------------------------- |
| 网格               | 例如 10 列 × 6 行                                           |
| 物品尺寸             | `sizeX × sizeY`（1×1 子弹、2×4 太阳能板）                        |
| 放置               | 物品占一个矩形区域，区域内**所有格必须空闲**                                |
| **自动摆放**         | 拾取时从左上向右下扫描，找**第一个放得下的位置**（first-fit）                   |
| **拖拽 / 旋转 / 拆分** | **本期不做交互**，但**数据结构必须支持**（见 §3.7）—— 用户 10:44 明确：这三项后续必须要 |

**为什么不做拖拽也能玩**：拾取自动找位，玩家不需要手动摆。拖拽只在"整理"时才需要，属于后续功能，**不是设计上砍掉**。

## 3.7 本节不做、但必须预留的三件事：拖拽 / 旋转 / 拆分

> 用户 2026-10-20 10:44：*"如果你是考虑到工作量那可以。后续我需要拖拽、旋转和拆分。（比如右键一沓堆叠了500张钞票，我可以选择拆分）"*

**定性：这三项是"延后"，不是"取消"。** 延后的只有 **UI 交互**（鼠标拖、右键菜单、旋转按钮），  
**数据结构和核心 API 必须本期就按"将来要做"的形态落地** —— 否则将来返工的是**存档格式和整个背包 UI**，不是加两个按钮。

### 三项各自的预留点

| 功能          | 本期必须就绪的东西                                                                                                                                              | 不做会怎样（返工代价）                                      |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| **拖拽**      | ① 每个条目的**放置坐标存在数据里**（`GridX / GridY`），不是 UI 临时算<br />② `TryAutoPlace(stack)`（first-fit 找位）与 `TryPlaceAt(stack, x, y, rotated)`（指定位置）**是两个函数**，前者内部调用后者 | 若把添加做成"找位 + 塞进去"的一体函数，将来拖拽要把整套添加逻辑劈开重写，并回头改所有调用点 |
| **拖拽（跨容器）** | ③ `ItemStack` 是可搬运的**独立值对象**，`InstanceId` **全局唯一**（不是容器内序号）                                                                                            | 若 uid 只在容器内唯一，背包→仓库搬运会撞 id，UI 拿着旧 id 指错物品        |
| **拖拽（预览）**  | ⑧ 必须有**纯查询接口** `CanPlaceAt(def, x, y, rotated)` —— 只回答"放得下吗"，**不改任何数据**。`TryAutoPlace` / `TryPlaceAt` 内部都调它                                            | 若"能不能放"和"放进去"写成一个函数，将来拖拽时鼠标划过就要真放进去，没法做半透明预览     |
| **旋转**      | ④ 每个条目存 `Rotated` 布尔<br />⑤ 占位尺寸统一走**一个函数** `GetFootprint(def, rotated)`（内部交换宽高），**不允许任何地方手写交换**                                                       | 若本期把"宽高交换"散落在放置/检测/绘制/存档四处，将来加旋转要全部找出来改，漏一处就是错位  |
| **拆分**      | ⑥ 每个条目有稳定 `InstanceId`（同拖拽第 ③ 条）<br />⑦ `TrySplit(uid, count, out newUid)` 的核心逻辑本期**实现**（约 10 行），只是**不给 UI 入口**                                        | 若靠 list 索引定位条目，拆分/丢弃后索引全变，UI 与数据不同步              |



### 为什么拆分"核心逻辑本期就写、UI 不做"

拆分的本质是"从条目 A 拿走 n 个，生成条目 B"，**它是"拾取/丢弃/合并"的公共底层**，不写反而要在别处重复实现一遍数量搬运。

而且本期就可能撞上真实场景：容器里有一条 500 张钞票，玩家背包剩余格数放得下但搬运逻辑必须知道"拿多少"。**函数先有、菜单后加**，是最省的做法。

### 拆分的约束（提前定死，避免将来含糊）

| 规则                       | 说明                                                  |
| ------------------------ | --------------------------------------------------- |
| 只能拆 `stackLimit > 1` 的条目 | `stackLimit = 1` 的东西本来就只有一个，拆不出来                    |
| `0 < count < 当前数量`       | 拆全部 / 拆 0 都不是拆分，应走别的操作                              |
| **失败必须整体回滚**             | 拆出来的新条目放不下 → 本次拆分作废，**不允许"半拆"**（数量已减、新条目没生成）        |
| 拆分不改变物品价值总和              | 500 张 × 100 = 拆成 200 + 300，`count × unitValue` 之和不变 |

### 拖拽将来会怎么用（写清楚，让现在的 API 形状有依据）

```
本期：  拾取 → TryAutoPlace(stack)              → 自动找空位
将来：  拾取 → TryAutoPlace(stack)              → 同上（不变）
        拖拽 → TryPlaceAt(stack, 鼠标格, 旋转态)  → 玩家指定位置
        跨容器 → 先从源容器 Remove(uid) → 再目标容器 TryPlaceAt(...)，失败则放回原位
```

**注意最后一条**：跨容器拖拽是"**拿走再放下**"，所以 `Remove` 必须返回完整的 `ItemStack`（含 uid、数量、旋转态），  
不能只是从列表里删掉。本期 `Remove` 就要返回完整条目 —— 这是免费的正确做法。

### 关于 `InstanceId` 要不要进存档

**不进。** `InstanceId` 只是**运行期句柄**（给 UI 和拖拽指代"哪一个条目"），读档时重新分配即可。  
存档只存「容器 → 条目列表 → `物品id / 数量 / GridX / GridY / Rotated`」。

这样存档格式干净、可读、可手改，也不会因为 uid 规则变化而需要迁移。  
（若将来真需要跨存档追踪某件物品，那是另一套"物品持久 id"的概念，与本期无关。）

### 一句话判据

> 本期&#x628A;**"东西放在哪、朝哪个方向、是哪一条"**&#x8FD9;三件事写进数据；  
> &#x628A;**"玩家怎么用手去挪它"**&#x7559;到后面。前者是地基，后者是操作。

### 13.3 容器搜索：**打开即自动顺序搜索**（推翻"长按 F 摸取"）

| 规则         | 说明                                                                         |
| ---------- | -------------------------------------------------------------------------- |
| **触发**     | **打开容器界面即开始自动搜索**，不需要对准物品按 F                                               |
| **顺序**     | **阅读顺序**（第一行左→右，第二行左→右…），即按 `(GridY, GridX)` 升序                            |
| **连续**     | 一件搜完**立刻**下一件，不等待、不需玩家操作                                                   |
| **中途退出**   | 搜索中或搜索完毕后**任何时刻**都可退出                                                      |
| **已搜出的保留** | 已搜出物品**再次打开无需重搜**                                                          |
| **未搜的保持**  | 未搜出的保持"未搜出"状态                                                              |
| **半途作废**   | ⚠️ **正在搜的那一件，退出即进度清零**。例：`searchSeconds = 3`，搜到 1.5s 退出 → 再次打开**重新从 0 开始** |

| **暂停**     | 搜索计时**不因打开其它界面而暂停**；只有关闭容器界面才停止（并作废当前进度）                                   |

**实现**：容器持有 `searchCursor`（第几条）+ `searchElapsed`（当前件已用时）。关闭界面 → `searchElapsed = 0`，`searchCursor` **不前进**。

### 13.16 医疗物品：**治疗池，可多次用**（用户 12:58 确认）

> 用户：**"治疗池，可多次用"** —— 保留现有手感，物品化只是把"池"从槽位移到物品实例上。

| 项      | 落地                                                                           |
| ------ | ---------------------------------------------------------------------------- |
| 定义侧    | `ItemDef.totalHeal`（该物品满池多少点）、`ItemDef.healPerUse`（每次消耗/治疗多少点，初始 **15**）     |
| 实例侧    | **`ItemInstance.remainingHeal`**（当前剩余池）—— **这是真实动态状态，必须进存档**                 |
| 单次使用   | 消耗 `min(healPerUse, remainingHeal)` 点池，治疗**等量**血量；剩余不足则**一次用完**（不浪费）         |
| 用完     | `remainingHeal == 0` → 物品**自动销毁**（离开容器）                                      |
| **堆叠** | **一律不可堆叠**（`stackLimit = 1`）：每个实例剩余量不同，天然不满足堆叠条件。与 §3.5 硬规则一致                |
| UI     | 格子内显示 **`剩余/满池`**（如「45/60」），让玩家看得出快用完了                                       |
| 施法感    | 沿用现有"施法 1 秒 + 每秒回一次"的节奏，**只把数值来源从槽位换成物品**                                    |
| 三种医疗物品 | `med_bandage` 1×1 / 25 池 ／ `med_firstaid` 1×2 / 60 池 ／ `med_kit` 2×2 / 100 池 |

**由此产生的一条重要存档要求**（写进 §13.6 的 DTO）：

```
{ itemId, x, y, rotated, count, remainingHeal }
```

- `remainingHeal` 对非医疗物品恒为 **0**（不占额外结构）
- **`InstanceId` 仍然不进存档**（运行期句柄），但 `remainingHeal` **必须进**（真实状态）

| 3 | 生成放不下  | **从队列尾部开始删，一直删到剩余全部装得下为止**；Console 输出明确警告（容器 id、删了几件、删了什么） |


**第 3 条的精确语义**（避免实现时理解偏差）：

```
抽取得到 [A, B, C, D, E]
按顺序 first-fit 放置：
  A 放下 → B 放下 → C 放下 → D 放不下 → 停止放置
从尾部删除直到全部可放：
  删 E？E 还没放。规则是"删最后一个排队的" → 删 E、再删 D → 剩 [A,B,C] 全部可放 → 结束
警告：容器 xxx 空间不足，丢弃 2 件（E, D）
```

- **不是**"跳过任意放不下的那一件"（那样会出现"D 被丢但 E 进去了"的怪现象）
- **必须记日志**：不静默丢失，但也不让容器崩掉

### 13.18 物品与网格底层设计**到此定稿**（容器系统见 §14）

- 全部歧义已清零：§12（15 条）+ §13（13 条纠正）+ 两轮追加确认（血包物品化 / 掉落表 / 医疗语义 / 抽取次数 / 放不下规则）
- **可以开工**，第一站 = 阶段 B（`ItemDef` + `ItemInstance` + `ItemContainer` + asmdef + EditMode 单测）
- 文档位置：`Docs/阶段7-设计说明.md`（§12 与 §13 以 §13 为准；§13.18 为本设计终点）

### 14.1 七处差异与处理

### 14.2 搜索耗时：**只由物品稀有度决定**

> 用户原话：*"取决于物品稀有度高低，和容器无关。"*

| 项         | 结论                                                                                                      |
| --------- | ------------------------------------------------------------------------------------------------------- |
| 归属        | `ItemDef.searchSeconds`（**物品定义上的字段**）；**容器不提供默认值**，也不参与乘法                                               |
| 默认值（按稀有度） | `Common` 1.5s ／ `Uncommon` 1.8s ／ `Rare` 2.5s ／ `Epic` 3.5s ／ `Legendary` 5s ／ `Exotic` 6s ／ `Ultra` 8s |
| 覆盖        | 允许逐件手改（Editor 提供"按稀有度填充建议值"按钮）                                                                          |
| 计时单位      | **按搜索条目**（一个堆叠条目 = 一次搜索，不按数量）                                                                           |
| 可配置       | 全部走资产配置，**不硬编码在逻辑里**                                                                                    |

### 14.3 中断：五种触发，全部**重置当前条目计时**

| 触发                                | 行为                                     |
| --------------------------------- | -------------------------------------- |
| **Esc**（关闭键）                      | 中断 + 关闭界面 + 重置当前条目计时                   |
| **移动键（WASD）**                     | **中断 + 关闭界面 + 立即恢复移动**（不允许"按了键却锁在原地"）  |
| **受击**（`PlayerHealth.Damaged`）    | 中断 + 关闭界面 + 重置计时                       |
| **离开交互范围**                        | 中断 + 关闭界面 + 重置计时（迟滞：退出距离 = 进入距离 × 1.5） |
| **战局结束**（`RaidDirector.Finished`） | 终止一切搜索与拾取                              |

**中断的语义（铁律）**：

- ✅ 保留：已发现状态、真实剩余物品、已拾取归属、本局生成结果、条目身份
- ⚠️ 重置：**只有当前正在搜的那一个条目**的计时 → 重开必须**重新连续搜满全程**
- ❌ 禁止：已发现物品退回未发现、重新生成、复制、删除

**拿取已发现物品不中断搜索**：鼠标点击/拖拽已揭示的物品属于正常操作，**不重置当前计时**（任务书 §7.3 明确要求）。

### 14.5 存入：**一直允许** + 三层防泄露

## 15. 容器等级影响爆率（用户 15:20 纠正，**覆盖 §13.15 的抽取流程**）

> 用户原话：*"我之前说不同容器不控制概率是错的，不同容器也有高低之分。容器种类也参加爆率调整，越高级的容器爆率也越高。"*
>
> ⚠️ 注意区分：**"容器无关"只适用于搜索耗时**（§14.2 不变）；**掉落概率是容器相关的**。

### 15.1 机制：两阶段抽取（先抽品质，再抽物品）

```
第 1 阶段：按「容器等级」抽一个品质（白/绿/蓝/紫/金/红）
第 2 阶段：在该容器的物品条目里，筛出这个品质的条目，按权重抽一个具体物品
```

对比旧方案（§13.15，单阶段按物品权重抽）：

| | 旧（单阶段） | 新（两阶段） |
|---|---|---|
| 高级容器怎么更容易出好货 | **靠人肉**把稀有物品权重调高 | **等级自动**决定品质分布 |
| 换一个容器 | 要重调整张权重表 | 只配「能出什么物品」+ 等级 |
| 概率是否 100% | 权重归一化 | 品质层天然 100%，物品层在品质内归一化 |

### 15.2 容器等级：**先定 3 档**（用户暂未定档数，此值可改）

| 值 | 枚举 | 中文 | 典型容器 | 边框色 |
|---|---|---|---|---|
| 0 | `Basic` | 普通 | 普通物资箱、纸箱、抽屉 | 灰 |
| 1 | `Improved` | 精良 | 工具箱、工业材料箱 | 绿 |
| 2 | `Elite` | 精英 | 医疗箱、军械箱 | 金 |

**命名刻意避开 `Common/Uncommon/Rare`** —— 物品品质已经用了这三个词，代码里出现两个 `Rare` 会混淆。

> 档数改成 5 档或 7 档时：**只加枚举值 + 加一行概率表**，抽取代码不用改。

### 15.3 品质概率表（**每行必须合计 100%**）

| 容器等级 | 白 Common | 绿 Uncommon | 蓝 Rare | 紫 Epic | 金 Legendary | 红 Exotic | 彩 Ultra |
|---|---:|---:|---:|---:|---:|---:|---:|
| **Basic 普通** | 60 | 29.4 | 9 | 1.5 | **0.09** | **0.01** | 0 |
| **Improved 精良** | 40 | 34.5 | 20 | 4.5 | **0.9** | **0.1** | 0 |
| **Elite 精英** | 10 | 25 | 40 | 19.4 | **5** | **0.6** | 0 |

- 表存在**全局资产**（如 `LootTierTable` ScriptableObject），3 行；将来加档只加行
- Editor 校验：**每行合计 ≠ 100 时报警告**（不阻断，运行时会归一化）
- **三档的金/红都不为 0**，只按档递增：金 `0.09% → 0.9% → 5%`，红 `0.01% → 0.1% → 0.6%`。`0.01%` ≈ 1/10000 几乎见不到，但**规则上存在**
- **全部是占位值，可直接改**；改完 Editor 重算合计并提示是否等于 100%
- 彩色 `Ultra` 全场 0：**预留档，本期任何容器都不出**

### 15.4 退化保护（不能空转、不能崩）

| 情况 | 处理 |
|---|---|
| 抽到的品质，该容器**没有对应物品** | **退回"全表按权重抽一个"** + Editor 警告（提示该容器缺这个品质的物品，建议补条目或调整等级表） |
| 品质表某行合计为 0 | 报错 + 该容器**退回全表抽取** |
| 品质表缺失（资产没配） | 报错 + 全部容器退回全表抽取（保证能跑） |
| 容器条目为空 | 报错 + 生成空容器 |
| 物品定义缺失 | 报错 + 跳过该条目 |

**为什么要有退化保护**：如果普通箱里只放了白色物品，但等级表有 9% 概率抽到蓝色，硬抽就会抽空。必须能兜底，且**在编辑器里能看出配置有问题**。

### 15.5 配置结构

```
【全局】LootTierTable（ScriptableObject）
  rows: [ { tier, qualityWeights[7] } ]      // 15.3 那张表

【每个容器】
  ContainerDef {
    tier              // Basic / Improved / Elite
    rollMin, rollMax  // 抽取件数范围，**每容器独立配**（占位示例 1~3；也可 1~5、2~4）
    entries[] {
      itemId          // 品质从 ItemDef 读，**条目里不重复填品质**
      weight          // 同品质内比较用的相对权重
      minCount, maxCount
    }
  }
```

**条目里不填品质** —— 品质由 `ItemDef.quality` 决定，避免两处配置不一致。

### 15.6 明确不受影响的部分

| 项 | 结论 |
|---|---|
| **搜索耗时** | **仍只看物品稀有度**（§14.2 不变）。高级箱里的物品稀有度高 → 自然搜得久，逻辑自洽 |
| **抽取件数** | 仍由 `rollMin ~ rollMax` 决定，**等级不参与**；**范围每容器独立配置，不是固定 1~3**（1~3 / 1~5 / 2~4 都合法，1~3 只是占位示例） |
| **允许重复** | 不变，同一种物品可在同一容器出现多次 |
| **尾部截断** | 不变（§13.17 第 3 条） |
| **生成时机** | 不变，战局初始化时一次（§14.6） |
| **确定性** | 不变，`LootRoll(containerId, raidSeed, tier)` 仍是纯函数；**等级是输入的一部分** |

### 15.7 完整抽取流程（实现照这个写）

```
LootRoll(containerId, raidSeed, tier, entries):
  1. 校验：entries 为空 → 报错，返回空
  2. count = randInt(rollMin, rollMax)        // 范围来自容器配置，与等级无关
  3. for i in 1..count:
       a. q = 按 tier 的品质表抽一个品质（权重归一化）
       b. pool = entries 中 ItemDef.quality == q 的条目
          if pool 为空 → pool = entries 全体，并记一次警告
       c. entry = 在 pool 里按 weight 抽一个
       d. n = randInt(entry.minCount, entry.maxCount)
       e. 生成实例（含 n 数量）→ 尝试放入网格
          if 放不下 → 尾部截断（§13.17）并警告
  4. 返回最终放入的条目列表
```

### 15.8 将来扩展（不重写）

| 想加的功能 | 怎么加 |
|---|---|
| 容器等级加到 5/7 档 | 加枚举值 + 加一行概率表，**代码不动** |
| 某容器保证出某个物品 | `entries` 加 `guaranteed` 标记（结构已留位，本期不实现） |
| 组合预设（如"主板+显卡成套出"） | 加一层 `presets`（本期不实现） |
| 红色物品只在专属容器出 | 让其它等级红色权重为 0，只有专属容器配红色概率 |
| 容器等级影响件数 | 把 `rollMin/rollMax` 从容器移到"等级表"，改动局部 |

| 项 | 结论 |
|---|---|
| 配置位置 | **每个容器自己的 `rollMin` / `rollMax`**，不是全局常量 |
| 合法值 | 1~3、1~5、2~4、3~3（固定 3 件）等**都合法** |
| 等级关系 | 容器等级**不影响件数**（用户 15:20 确认；将来想改成影响，见 §15.8 扩展表） |
| 校验 | `rollMin ≥ 0`、`rollMax ≥ rollMin`；非法则报错并回退 `1~1` |
| 代码要求 | **不允许在逻辑里写 `3` 或 `1` 这类字面量**，一律读配置 |

**文档里所有"1~3"字样都只是占位示例**，已在 §13.15、§13.17、§15.5~15.7 逐处标注。

#### ③ 低概率怎么验证（很实际的问题）

`0.01%` 意味着平均 1 万次才出 1 次。**手动开箱子验证几乎不可能**，所以：

| 手段 | 做法 |
|---|---|
| **单元测试用统计** | 固定 seed，对同一容器抽 **100,000 次**，统计各品质次数，断言与配置概率的偏差在容差内（如 ±15%） |
| **可注入 RNG** | `LootRoll(..., IRandom rng)` —— 测试时注入确定序列，正式时用默认随机 |
| **Editor 调试按钮** | 「按当前配置抽 1 万次并打印分布」：一眼看出配置是否写错（不需要真玩游戏） |
| **强制品质开关** | 调试用：`forceQuality`，指定后跳过第一阶段直接抽该品质，方便验证"某品质的物品池对不对" |

> 这几条都是**测试设施**，不改变生成规则本身。

### 16.3 测试抓到的真 bug（已修，值得记住）

**现象**：`TryAdd(Cpu, 3)` 只生成 **1 条 `count=3`**，而不是 3 条独立条目 —— 等于把三件独立物品合并了。

**根因**：`TryAdd` 的第二步按「剩余数量」切块：
```csharp
int chunk = def.IsStackable && remaining > def.StackLimit ? def.StackLimit : remaining;
```
对 `StackLimit = 1` 的不可堆叠物品，`IsStackable` 为 false → `chunk = remaining = 3`。

**危害**：直接违反用户定的铁律「两把属性完全相同的 AK47 不可以堆叠」。

**修复两处**：
1. `ItemContainer.TryAdd`：不可堆叠时 `chunk = 1`，逐条创建
2. `ItemStack.Create`：`maxCount = StackLimit > 1 ? StackLimit : 1`，不可堆叠强制 `Count = 1`

> **这就是写单测的理由**：这个 bug 在 UI 上完全看不出来（玩家看到"3 个 CPU"），
> 只有数条目数才暴露。没有测试的话，它会一直潜伏到存档阶段，变成「重开游戏后 3 个 CPU 变 1 个」的灵异事件。

### 16.4 与设计的一处偏离（说明原因）

`LootRoller` 里原本用 `readonly struct Candidate` + 返回 `null` 表示「没抽到」——
**struct 是值类型，不能用 null**，编译直接报 `CS0037`。
改用 `TryPickWeighted(..., out Candidate picked)` 返回 bool。语义更清晰，也没有装箱。

### 17.2 为什么"资产层"和"纯数据层"必须分两层

```
ItemDefinitionAsset（Unity 资产：能拖图标、能在 Inspector 填）
        │  ToDef()
        ▼
ItemDef（Core 纯数据：规则唯一真源，零 UnityEngine 依赖）
```

如果让 Core 直接继承 ScriptableObject，就有两个后果：
① Core 无法被 EditMode 单元测试覆盖（这正是阶段 B 花了大力气避免的）；
② 规则层绑死 Unity，将来把生成逻辑搬到服务器时要重写。

**约定：规则只认 `ItemDef`。** UI / 容器 / 存档都不直接读资产 —— 否则会出现"资产里改了但运行时没生效"这类极难查的问题。
唯一例外是**图标**：`Sprite` 属于表现，只能挂在资产上，UI 通过 `ItemDatabase.TryGetAsset(id, out asset)` 拿。

### 17.6 两个坑（都是实际踩到才发现的）

**坑 A：`TMP_Settings.defaultFontAsset` 是静态属性**

```csharp

TMP_Settings.defaultFontAsset      // ✅
```

**坑 B：Dynamic 字体资产不持久化已光栅化的字形**（这个更值得记）

生成后我读 .asset 检查，发现图集只有 **1×1**、字符表 **0 条**，第一反应是"字体坏了"。
实测结论：**这是 Dynamic 的设计，不是 bug** —— 字形在运行时按需生成，不会写进资产。

因此验收标准必须是「**能不能真的渲染出汉字**」，而不是「字符表有多少条 / 图集多少像素」。
`VerifyOnly` 因此改成**渲染探针**：临时建一个 3D `TextMeshPro`（不需要 Canvas，无头环境可用），
塞一段中文，`ForceMeshUpdate()`，再数可见字符数与顶点数。

> 空格本来就不可见。第一版断言写成 `visible == characterCount`，结果永远 10/12 → 看起来像字体坏了。
> **又是我断言写错、不是产品错**（和阶段 B 那次一样）。现在的断言是「可见数 == 非空白字符数」。

### 18.2 三层职责，各自只做一件事

```
ContainerRole + ContainerDef      图纸：多大、能装什么、出什么货
        ↓ ContainerFactory.Create
ContainerInstance                 实物：这一只箱子此刻装着什么 + 玩家已经发现到哪一步
        ↓ （容器-3 接管）
搜索计时                          本次连续搜索进度（**故意不在上面任何一层里**）
```

**为什么生成只允许在 Factory 里发生**：
需求是「打开容器不能重新抽取」。最稳的做法不是"打开时小心点"，而是**让生成根本不在打开路径上** ——
打开只能读 `Instance.Contents`，而 Contents 只在 `Create` 时被填过一次。
这样"重复生成"从架构上就不可能，而不是靠开发者每个入口记得别调。

### 18.3 搜索队列的三个设计决定

**① 条目身份用 `EntryId`，不用数组下标**

拿走一件物品后列表会变短，下标一挪就会把「已发现」错记到别的物品上，或直接跳过某个未发现的物品。

**② 拿走物品只标记 `Taken`，不删条目**

删了会让后续条目的相对顺序改变。条目不删，身份和顺序就永远稳定。

**③ 当前搜索进度**（已搜了几秒）**故意不存在任何数据类里**

这是 §14.3 定死的规则："中断后当前未发现物品的计时必须整体作废"。
如果 `elapsed` 存在条目上，就必须在**每个**中断入口记得清零 —— 关界面、按移动键、受击、
走出范围、战局结束，漏一处就是"关掉再打开进度还在"的 bug。
现在它由搜索流程（容器-3）持有为**局部变量**，界面一关自然归零。

**顺序规则**：首次建队列按**行优先**（从上到下、从左到右）排序，与玩家在网格里看到的顺序一致；
玩家后续存进来的物品**追加到队尾**（设计允许一直存入，存入的东西要能搜到）。

### 18.4 确定性：为什么需要 `InstanceKey` + `raidSeed` 两个东西

| 用什么做种子 | 会出什么问题 |
|---|---|
| 只用容器定义 ID | 场景里两只"普通物资箱"会抽出一模一样的东西 |
| 只用位置坐标 | 挪一下箱子，内容就变了（不该变） |
| **实例标识承担"是哪一只"、本局种子承担"哪一局"** | 同标识同种子 → 永远同一堆东西；换局 → 全新一批 |

所以 `LootableContainer` 有一个必须手填的 `instanceKey`（如 `crate_01`）。
两只箱子重名时会在 Console 明确警告 —— 这是配置错误，运行时无法自动修。

**种子何时换**：`RaidSession` 订阅 `SceneManager.sceneLoaded`。
选它而不是某个脚本"趁早"调用，是因为 Unity 的顺序是
「场景内所有 Awake/OnEnable → sceneLoaded → 所有 Start」，而容器在 `Start` 里创建 ——
这样换种子一定**早于**容器创建，不会出现同一场景里两只箱子用了不同种子的错位。

### 18.7 测试抓到的一个真设计缺陷（已修）

**现象**：`搜索耗时取自物品定义` 这条用例失败 —— 期望 1.8 秒，实际 2.0 秒。

**根因**：我最初的做法是"生成时从战利品表反查，缓存一张 `物品ID → 搜索耗时`"。
但容器里的东西**不只来自战利品表** —— 玩家会往容器里存东西（设计明确允许一直存入），
那些物品不在缓存表里，就会退化成默认 2 秒。

**后果**：玩家会发现"搜自己刚放进去的东西特别快"，而稀有物品本该慢慢搜。

**修法**：`ContainerInstance` 持有物品目录，`ResolveSearchSeconds` **每次直接查定义**。
只多一次字典查找，但任何来源的物品都正确；顺带删掉了"必须先生成后灌表"的顺序约束。

### 18.9 修正：玩家存入的物品必须保持「已发现」（2026-10-21 06:44，用户实测反馈）

> 用户原话：*"当玩家把已有的东西放进容器，这个物品不需要再搜索一遍。比如玩家已经获得了一个物品：CPU。玩家拖拽回容器内，这个物品应该依旧是一颗 CPU，且是已搜索状态，不会变成灰色需要搜索。"*

**现象**：玩家把自己认识的物品放进容器，它会进入搜索队列且 `Revealed = false` → 界面上是灰的，还得重新搜一遍。

**根因**：`SyncEntries()` 对所有新条目一律 `Revealed = false`。
它只区分了"新出现的物品"，没区分**这件东西是谁弄进来的**：
战利品是玩家没见过的（要搜），玩家手上的东西是他自己拿着的（当然认识）。

**修法**：

| 改动 | 说明 |
|---|---|
| `SyncEntries(bool newEntriesRevealed = false)` | 生成路径传 `false`（未知）；玩家操作路径传 `true`（已知） |
| **新增 `TryStoreFrom(source, uid, out reason)`** | 转移进容器 + 自动标为已发现。交互层**只准用这个**，不要自己 `TryTransferTo` + 手动同步 |
| **新增 `TryTakeTo(target, uid, out reason)`** | 转移出容器 + 标记取走；**未发现的物品直接拒绝**（玩家根本看不到，不该出现在可拾取列表里） |
| `LootableContainer.RefreshAfterContentChanged(bool)` | 降级为"兜底重对齐"，并在注释里写明别拿它当搬运 API |

**为什么这样不会泄露容器里原有的未知物品**：
跨容器转移走的是 `TryAutoPlace`，**不会合并进已有堆叠**。
所以玩家存进来的东西永远是一条独立条目，「已发现」可以单独给，
箱子里原有的未知堆叠不受影响。
（如果将来做"快速存入"用了 `TryAdd`，就会合并——那时必须重新考虑，
在 `TryStoreFrom` 的注释里已经写明了这条前提。）

**顺带补的一条规则**：`TryTakeTo` 会检查条目是否 `Revealed`。
未搜出来的东西不可拿走 —— 否则 UI 一列"容器里所有物品"就能绕过搜索直接白拿。

**验证**：EditMode **95 / 95 通过**（新增 5 条）

```
玩家存入的物品_直接算已发现_不需要再搜          Passed
玩家存入_不会泄露容器原有的未发现条目            Passed
未发现的物品不能被拿走                        Passed
已发现后拿走_条目标记取走且不影响其他条目         Passed
玩家存回同一件物品_依然可被再次取走              Passed
```

**教训（会反复用到）**：
凡是"某个状态由多条路径共同维护"的地方，就是 bug 温床。
这次的问题不是逻辑写错，而是**入口太多** —— 谁都能调 `SyncEntries()`，
于是"该传 true 的那次"被漏掉了。
收敛成 `TryStoreFrom` / `TryTakeTo` 两个语义明确的方法后，
调用方不需要知道"要不要标记已发现"，也就不可能忘。

### 19.3 开局携带基线：为什么是 `uid → 数量` 而不是两种朴素做法

需求：撤离结算必须**剔除开局自带的东西**（§13.7）。基线在 `EnsureBuilt` 末尾自动记录。

| 朴素做法 | 会错在哪 |
|---|---|
| 只记"开局物品 ID 列表" | 开局带 1 个绷带、用掉又捡到 1 个 → 分不清哪些是本局赚的 |
| 只比对 uid 集合 | 开局带 30 发子弹，捡到 30 发**合并**成一条 60 发（uid 不变）→ 这 30 发会被漏算 |
| **记 `uid → 数量`** | 每条的增量 = `当前数量 - 开局数量`，堆叠合并也算得对 |

`ComputeGainsSinceRaidStart()` 的规则：
- 基线里没有的 uid → 整条都算本局新增
- 基线里有、数量变多 → 只算多出来的部分
- 数量变少（用掉了）→ 算 0，**不做负数抵扣**（否则"用掉 3 个开局血包"会抵掉本局收益）
- 只提供数据，**真正入库/发钱在撤离结算（阶段 G）**

## 21.9 首次实机反馈后的修正（2026-10-21 10:56 用户实测，**已全部修复**）

> 用户第一次 Play 后报了 5 个问题。其中 ①④ 是**真 bug**，②③ 是**设计变更**，⑤ 是**范围约定**。

### ① 「打开容器只出现一个『主』字，没有任何物品」—— uGUI 的负尺寸陷阱

**这是本轮最有价值的 bug。** 现象是"物品块完全不可见，只剩一个汉字浮在格子上"。

**根因**：`UiFactory.Inset()` 对**点锚点**（`anchorMin == anchorMax`）用了 `offsetMin/offsetMax` 的写法：

```csharp
// 错：只对拉伸锚点成立
rt.offsetMin = new Vector2(inset, inset);
rt.offsetMax = new Vector2(-inset, -inset);
```

对点锚点，`offsetMin/offsetMax` 与 `sizeDelta/anchoredPosition` 是同一组自由度的两种表示，写进去相当于把 **sizeDelta 算成了 `offsetMax - offsetMin = (-2·inset, -2·inset)`** → 物品块变成 **-3×-3** → 整个节点不渲染。

而里面的文字（TMP）按自身文本边界绘制，不受父节点负尺寸约束 → **只剩一个"主"字**。这完美解释了用户看到的现象。

**修正**：`Inset` 分两种锚点处理 —— 拉伸锚点走 offset，点锚点走 `sizeDelta -= 2·inset` 并按 pivot 把位置往里挪。

> 记入速查卡 **坑 #26**。判断口诀：**点锚点下 `offsetMin/offsetMax` 会把尺寸算成两者之差，不是"内缩"**。

原来是纯色块 `(0.20, 0.21, 0.25)`，跟格子背景亮度差太小，玩家分不清"有东西"和"空格"。

新增 `Gameplay/Inventory/UnknownCellGraphic.cs`（自绘 `MaskableGraphic`）：

| 层 | 内容 |
|---|---|
| 填充 | `(0.028, 0.031, 0.040)` —— **比格子背景更暗**，形成"凹进去"的观感 |
| 斜纹 | 45° 线族 `u - v = c`，间距 7.5px、粗 1.6px、白色 5.2% |
| 边框 | 1px，白色 17% |

**斜纹不裁切的算法**：对每条 `c`，线段在矩形内的可见部分被 `[0, w]` 与 `[c, c+h]` 两个约束夹住，
取交集即为可见段。**不需要 `RectMask2D`，也不需要为每块格子建子节点** —— 一个 Graphic 画完。

### ② 放大镜「转的位置不对」→ pivot 必须在中心

`SearchLens` 用 `localRotation` 做旋转，而**旋转永远绕 pivot**。原来 `_lens.pivot = (0, 1)`（左上角），
所以放大镜是绕着格子左上角"甩"，不是自转。

修正：`pivot = (0.5, 0.5)`，定位改为直接给"物品矩形的中心点"
（pivot 在中心时 `anchoredPosition` 恰好就是中心相对父节点左上角的偏移）。

### ③ 放大镜将来是贴图 —— 现在留好入口

`InventoryGridView` 新增 Inspector 字段：

| 字段 | 作用 |
|---|---|
| `lensSprite` | **留空 = 用代码自绘圆环 + 手柄**（灰盒兜底）；拖一张 png 进来就自动换成贴图，**代码一行不用改** |
| `lensScale` | 放大镜占物品短边的比例（默认 0.62） |
| `lensColor` | 自绘模式下的颜色（有贴图时不生效） |
| `unknownFill` / `unknownHatchSpacing` | 未知块的填充色与条纹间距，可在 Inspector 调 |

### ④ 「拖拽时按 R 有时没反应」→ 两个原因

| 原因 | 说明 |
|---|---|
| **鼠标不动时 `OnDrag` 根本不触发** | 平滑移动才会触发 `IDragHandler.OnDrag`；停下后按 R 没有任何人调 `UpdateDrag` |
| **同一帧被调用两次** | `InventoryUi.Update` 和 `ItemCellView.OnDrag` 可能同帧都进来 → 一次按 R 翻转两次 → 等于没转 |

修正：
- `Update()` 里每帧用"最后的鼠标位置"主动调一次 `UpdateDrag`（`_lastDragScreenPos`）
- R 的消费加**同帧去重**（`_lastRotateFrame`），一帧只翻一次
- 旋转时打一条日志（`旋转 → 横放/竖放`），方便确认到底是没收到还是不允许旋转（`AllowRotate = false` 的物品仍然转不了，这是对的）

### ⑤ 打开界面时隐藏右下角弹药数量

`AmmoHud.OnGUI` 开头加 `if (InteractionMode.AnyOpen) return;`。

理由：看物品时弹药数字既没用，又会压在界面右边缘上。走 `InteractionMode` 而不是自己判断
"有没有 UI"，是为了和光标 / 禁开火共用同一个状态源。

## 21.11 第三轮实机反馈：放大镜动画与格子样式（2026-10-21 11:44，**代码完成，编译待验证**）

### ① 放大镜不该自转 → 改成「摆动 + 浮移」

用户原话：*"谁家放大镜这样转啊，我要的是整个放大镜像搜索那样动，放大镜的柄永远指右下方。"*

上一版是 360° 匀速自转（`localRotation` 每秒 -220°）。问题不在数学，在**隐喻**：
真实的放大镜是"人拿着它在摸索"，手柄方向基本不动，整体小幅晃；转一整圈看起来像风车。

改成：

| 参数 | 值 | 效果 |
|---|---|---|
| `swayDegrees` | **9°** | 角度在 ±9° 之间正弦来回 —— 手柄始终朝右下 |
| `swaySpeed` | 5.5 | 摆动快慢 |
| `bobPixels` | **1.8 px** | 两个不同频率的正弦叠加做浮移，看起来不像机械往复 |

**结构上的改动（重要）**：把动画拆到**内层节点 Sway**：

```
SearchLens      ← 外层，位置 = 物品中心（由 InventoryGridView 每帧定位）
 └─ Sway        ← 内层，只做旋转与偏移（由 SearchLens 驱动）
     ├─ Ring / Icon
     └─ Handle
```

为什么拆两层：外层位置每帧可能被 `PositionLens` 重设，内层偏移由动画累加。
混在一个节点上会互相覆盖（上一版"位置乱"的根因之一）。

**将来换贴图**：这套摆动对图片同样成立，`lensSprite` 拖进去就行。

### ② 格子：去斑马纹 + 把"粗分割线"改成细线

用户：*"不要用斑马纹，并且中间为什么有比较粗的分割线？改成和我图片里一样的格子。"*

| 问题 | 根因 | 修法 |
|---|---|---|
| 斑马纹 | 格子交替 `alpha 0.045 / 0.075`（当初为了"方便数格子"） | 统一 `CellFill = (1,1,1,0.045)` |
| 粗分割线 | 每格 `Inset(1px)` → 相邻缝隙 **2px** | `Inset(0.5px)` → 缝隙 **1px** |
| 线太暗，不像网格 | 缝隙透出的是面板底色（很暗） | 新增 **`GridBackdrop` 底板** `(1,1,1,0.085)`，缝隙透出它 → 细而清晰的网格线 |

底板尺寸 = 整个网格（`Width×cell × Height×cell`），排在最底层（`SetAsFirstSibling`），
格子画在它上面、每格只留 0.5px 边 → 缝隙就是 1px 的线。**不需要为每条线建节点。**

### ③ 顺带修掉一个潜伏的层级 bug

`_itemsRoot`（物品层）在 `Build()` 里创建，而格子是在 `RebuildCells()` 里后创建的
→ **物品层一直被压在格子下面**（因为格子的 alpha 只有 0.045，肉眼几乎看不出来，
所以之前没被发现）。现在每次重建格子后显式 `_itemsRoot.SetAsLastSibling()`。

## 21.12 揭示特效与开关动画（2026-10-21 11:58，**代码完成，编译待验证**）

> 用户要求：搜索出的瞬间"先放大再回正常 + 发光（仅高品质）"；打开/关闭"从右侧渐显滑出，只移动一小段"。

### ① 揭示动画：倍率随品质递增

**倍率表**（用户定：白色 1.02 起，最高不超过 2.0）：

| 品质 | 倍率 | 光晕 |
|---|---:|---|
| 白 Common | **1.02** | ❌ |
| 绿 Uncommon | 1.06 | ❌ |
| 蓝 Rare | 1.14 | ❌ |
| 紫 Epic | 1.30 | ✅ |
| 金 Legendary | 1.50 | ✅ |
| 红 Exotic | 1.75 | ✅ |
| 彩 Ultra | **2.00** | ✅ |

- 白/绿几乎察觉不到（1.02/1.06），越稀有"跳"得越明显 —— 这本身就是一种品质提示
- 时长也跟着走：`0.20s + (倍率-1) × 0.22`，白色约 0.20 秒、彩色约 0.42 秒
- 缓动用 **EaseOutBack**（末尾过冲）而不是线性 —— 会先缩到略小于 1 再回正，有"啪一下落定"的手感

### ② 光晕：自绘径向渐变

新增 `Gameplay/Inventory/GlowGraphic.cs`：

- 顶点 0 = 圆心（不透明），一圈 48 段的边缘点（**全透明**），画成三角形扇 → 径向渐变
- 挂在物品块的**下层**（`SetSiblingIndex` 到物品之前）→ 中心被物品盖住，只露外圈的光
- 动画：尺寸 `0.95 → 2.4` 倍物品短边，alpha `0.85 → 0`，0.55 秒
- 颜色 = `ItemQualityPalette.Of(品质)`

**为什么不只做"物品块自己变亮"**：用户选的是"外围彩色光晕"—— 那才有"从里面透出光"的感觉；
整块变亮只是闪一下，看不出光从哪里来。

### ③ 开关动画：右偏 80px + 淡入

用户明确：**不是从屏幕外飞进来，只移动一小段**。

| 项 | 值 |
|---|---|
| 位移 | **80 px**（向右偏，然后滑回原位） |
| 时长 | **0.18 秒** |
| 缓动 | EaseOutCubic（起步快、收尾稳） |
| 实现 | `CanvasGroup.alpha` + `_root.anchoredPosition.x` |

**关键的两处顺序**（否则会有"输入错乱"或"光标跳变"）：

1. **打开时先 `InteractionMode.Push` 再起动画** —— 淡入的 0.18 秒里也不该还能开枪
2. **关闭时先不 Pop，等淡出播完再 Pop**（`FinishClose`）—— 否则界面还在淡出、光标已经跳回准星
3. 淡入/淡出期间 `blocksRaycasts = false` —— 防止点到"半透明状态"的按钮

### ④ 一个必须处理的边界：动画期间重复按 Tab

玩家可能在关闭的 0.18 秒内又按 Tab 打开。若不处理，两个动画会抢同一个
`_rootAnimating`，`InteractionMode` 的 Push/Pop 次数会错位（输入被永久锁住）。

修法：`OpenBackpack / OpenContainer` 开头调 `FinishCloseIfRunning()`，把未完成的关闭**就地收尾**再打开。

### ⑤ 揭晓动画的触发条件

`InventoryGridView` 维护 `_revealedSeen`（已见过的条目 uid）：

- **首次 `Refresh` 只登记、不播** —— 否则打开一个搜了一半的箱子，已搜出的会整屏一起弹
- 之后每次 `Refresh`，凡"已 revealed 且不在集合里"的就是**刚搜出来的** → 播动画
- 换容器（`Build`）时清空集合

物品被拿走再存回（uid 不变）不会重复播。新抽到的（新 uid）会播。

## 21.14 光晕修正 + 动画提速 + 两个红物品（2026-10-21 12:31，**代码完成，物品资产待生成**）

这就是"方形径向渐变"的定义。

| 参数 | 值 |
|---|---|
| `gridSegments` | 5（36 顶点 / 50 三角形，200px 内看不出棱角） |

### ② 「搬一次亮一次」的真 bug

## 21.16 「打开容器不搜索」的真正根因 + F 返还 + 自适应落点（2026-10-21 13:30，**代码完成，编译待验证**）

用户三条反馈：

> "一个是我需要允许玩家对准背包里的物品按下F返还给容器，
> 第二个是打开容器不搜索的问题还是存在。
> 另外，我想要物品可以自适应位置并旋转。例如背包只剩1×4的空间，
> 当前玩家拖动一个4×1的物品到背包空间附近时自动旋转成1×4格式。"

### ⚠️ 先纠正 §21.15 ③：那个诊断只对了一半

上一轮把"偶尔不搜索"归因于"Session 握着旧实例"，修了 `ResetForNewContent()`。
用户复测**仍然存在**。这次把三条路径全查了一遍，找到**两个真正的主因**：

#### 主因 A：中断逻辑绕过了交互仲裁（`WantsToMove`）

```csharp
// 旧代码
bool WantsToMove()
{
    var input = GameInput.Instance;
    Vector2 move = input.MoveValue;          // ← 读的是**原始输入**
    return move.sqrMagnitude > t * t;
}
```

`GameInput.MoveValue` 是 `InputAction.ReadValue` 的裸值，**不经过 `InteractionMode`**。
而搜索界面推的是 `UiDemand.SearchLike`（含 `BlockMove`）——
真正被挡住的是 `PlayerInputReader`，`GameInput.MoveValue` 照样非零。

于是最坏组合出现了：

> 玩家**一边按着 W 走向箱子，一边按 F** →
> 界面开、会话建 → **下一帧** `WantsToMove()` 为真 → `AbortSearch("移动输入")` →
> 进度作废、放大镜消失、什么也没搜。

**而且没有任何提示**，玩家只会觉得"这箱子坏了"。

设计 §8.3 的原意是"不能让玩家按了键却被无反馈地锁在原地"。但现在移动权已经在界面手里
（`BlocksMove`），玩家按 W 本来就走不动 —— 再因此中断搜索就只剩惩罚。

**修法（两道保险）**：

```csharp
if (InteractionMode.BlocksMove) return false;   // 界面已经收走移动权，不再判"想走"
```

外加 `_begunFrame`：搜索开始的那一帧**不判**移动输入，
防止"按 F 那一帧 W 还按着"的残留边沿把刚建立的会话打掉。

> 副作用：`abortOnMoveInput` 在"开界面搜索"这条路上从此不生效（这是对的）。
> 将来如果做"不打开界面也能搜"（比如趴在地上摸尸体），这个判定会自动复活 —— 不需要改代码。

#### 主因 B：站在几只箱子中间按一次 F，**所有**箱子同时开始搜

```csharp
// 旧代码：ContainerSearchDriver.Update
if (!IsSearching) { TryBeginByInput(); return; }   // ← 谁在范围内谁就开始搜
...
void TryBeginByInput() {
    if (!input.InteractPressedThisFrame) return;
    if (!InRange(interactRange)) return;
    BeginSearch();                                 // ← 每只箱子各判各的
}
```

可测试箱是**并排摆的**（`container_test_lux`、`container_test_rich` 等都在 3 米内）。
按一次 F：

| 箱子 | 结果 |
|---|---|
| A（界面显示的那只） | 正常搜，有放大镜 |
| B、C（在范围内但没打开） | **也在后台开搜**，而且没人看得见 |

B、C 会一路 `Tick` 到全部揭示。等玩家真的走过去打开 B：

```
OpenContainer(B) → BeginSearch() → Session.Begin() → PendingEntry == null → Finish() → false
```

→ **没有待搜条目 → 没有放大镜 → "这箱子不搜索"**。

这也完美解释了"为什么用调试刷新之后更容易碰上"：刷新把所有箱子变回未搜状态，
站过去一按 F 又全都开始搜一遍。

**修法**：只有「界面右列正在显示的那一只」才允许被 F 触发：

```csharp
if (!IsDisplayedInUi()) return;   // 其余箱子一律不许自己开搜

bool IsDisplayedInUi()
{
    InventoryUi ui = InventoryUi.Instance;
    if (ui == null || !ui.IsOpen) return false;
    if (_container == null || _container.Instance == null) return false;
    return ui.CurrentContainer == _container.Instance;
}
```

这样"何时开始搜索"就只有**一个**入口：`InventoryUi.OpenContainer()`（它知道玩家选了哪一只）。

#### 顺带：把"中断"变成可见 + 可续

光修根因不够 —— 受击 (`abortOnDamage`) 和走出范围仍然会让搜索中断，
而玩家看到的依然只是"放大镜突然不动了"。所以补两条：

| 补充 | 说明 |
|---|---|
| `TickSearchWatchdog()` | 检测"从搜索中 → 不在搜索中"，并且 `PendingCount > 0` 时弹 Toast：`搜索已中断（受到伤害（3））　按 F 继续` |
| F = 继续搜索 | 鼠标没指着任何物品时按 F → `ContinueSearch()`。否则玩家只能关掉界面再按一次 F（进度反正都要重来） |

另外 `OpenContainer` 里 `BeginSearch()` 失败时也从"只打日志"改成**弹 Toast**
（`这个容器里没有可以搜索的东西了`）—— 让"空箱子"和"界面坏了"能区分开。

### ① F 返还：随身容器 → 地图容器

用户要求：*"允许玩家对准背包里的物品按下F返还给容器。"*

F 现在有**三条**路径，按优先级在一个入口里判断（`OnInteractPressed`）：

| 顺序 | 指着什么 | 动作 | 走的 Core 方法 |
|---|---|---|---|
| ① | 地图容器里的物品 | 拿进随身容器（背包 → 弹挂 → 口袋） | `ContainerInstance.TryTakeTo` |
| ② | 随身容器（背包 / 弹挂 / 口袋）里的物品，**且地图容器开着** | 放回地图容器 | `ContainerInstance.TryStoreFrom` |
| ③ | 什么都没指到 | 继续搜索 | `ContainerSearchDriver.BeginSearch` |

**为什么统一成一个入口**：三种含义散在三处判断，迟早出现"同一次按键命中两条"
（比如既拾取又继续搜索）。现在只有 `Update()` 里的一句话派发。

**为什么"返还"必须走 `TryStoreFrom` 而不是 `TryTransferTo`**：
`TryStoreFrom` 会把新条目直接标成 `Revealed = true`。
用裸转移的话，玩家自己的东西放回箱子会**变灰**、还得重新搜一遍才拿得出来
（`ContainerInstance` 的注释里专门警告过这条）。

#### 顺带修的一个"拿错东西"隐患

原实现把 `_hoveredCell`（一个 `ItemCellView`）当作 F 的目标。
但物品块是**池化复用**的：一次 `Refresh()` 就可能让同一个节点去显示另一件物品，
而"鼠标没动"时不会再触发 `OnPointerEnter` ——
于是 `_hoveredCell.Owner/Stack` 可能已经指向**别的**物品。

现在改成记**身份快照**：

```csharp
ItemContainer _hoveredOwner;
long _hoveredUid;
```

按 F 时用 `_hoveredOwner.Find(_hoveredUid)` 重新确认那件东西还在，不在就当"没指着"。

### ② 自适应位置 + 自适应旋转

用户要求：*"物品可以自适应位置并旋转。例如背包只剩1×4的空间，
拖动一个4×1的物品到背包空间附近时自动旋转成1×4格式。"*

`InventoryUi.UpdateDrag` 改成**四级尝试**，第一个成功的就是落点：

| 级 | 位置 | 朝向 | 意图 |
|---|---|---|---|
| ① | 鼠标精确位置 | 当前朝向（玩家按 R 选的） | 玩家指着哪就是哪，最优先 |
| ② | 鼠标精确位置 | **另一朝向** | 只剩 1×4 竖缝时把 4×1 自动转过来（用户原话的例子） |
| ③ | **附近（半径 2 格）** | 当前朝向 | 指得偏半格 / 贴着网格边缘也能落下 |
| ④ | 附近（半径 2 格） | 另一朝向 | 上面两条的组合 |

两个关键实现细节：

**（a）换朝向后格位必须重算。**
`ScreenToGrid` 是"用物品中心反推左上角"，1×4 和 4×1 的中心差半格。
所以第 ②④ 级会用新 footprint 再调一次坐标换算，不能复用旧的 `gx/gy`。

**（b）"意图"和"结果"必须分开存。**

```csharp
bool _dragRotated;        // 玩家按 R 表达的意图
bool _dragCommitRotated;  // 这一格实际会用的朝向（可能是自动转过来的）
```

混成一个字段的话，鼠标一移开那块空地，物品就**永久**转过来了，
玩家会以为"R 键没反应"（其实是被自动旋转覆盖了）。
现在 `UpdateGhost` / `ShowPreview` / `Commit` 全都读 `_dragCommitRotated`，
`_dragRotated` 只由 R 键改。

**（c）为"吸附"新增 `InventoryGridView.ScreenToGridRaw`。**
原来的 `ScreenToGrid` 在越界时直接返回 false —— 也就是说，把 4 格高的物品拖到网格
**上边缘附近**时，算出的 `gy` 是负数 → 整个拖拽直接判红，**哪怕往下一点就有位置**。
（这是个大件拖拽的老毛病，之前一直存在。）

现在拆成两层：

| 方法 | 越界时 | 用途 |
|---|---|---|
| `ScreenToGridRaw` | 照常返回原始格位（可为负） | 给吸附用 |
| `ScreenToGrid` | 返回 false | 保留给需要"严格在格内"的场合 |

`UpdateDrag` 改用「鼠标是否落在网格矩形内」（`ContainsScreenPoint`，由 `FindGridAt` 负责）
来判断"在不在这个网格"，格位是否合法交给 `CanPlaceAt` + 吸附 —— 两件事不再混在一个判定里。

`TrySnap` 由近到远按**切比雪夫距离**一圈一圈找（只扫每圈边界，内圈上一轮已试过），
最坏 5×5×2 = 50 次 `CanPlaceAt`，每次是对 mask 的范围检查，开销可忽略（只在拖拽时跑）。

**为什么吸附不会让人误解**：预览框（绿/红）始终把**实际落点**画出来，
顶部提示还会追加 `已自动转向` / `已自动就近对齐`，玩家看得见东西落在哪。

## 21.17 光晕跟随物品轮廓 + 修「光晕卡在原地」（2026-10-21 13:35，**代码完成，编译待验证**）

用户反馈两条：

> "如果鼠标对准未搜索的物品狂按 F，在被背包拾取后光晕会卡在原地，
> 另外我像你确认一下，1×1 的物品就是 1×1 的光晕，2×4 则是 2×4 的光晕。"

### ① 光晕卡在原地（真 bug）

**先回答**：不是"没清除"，是**清不到**。

`ItemCellView.SpawnGlow()` 把光晕建成 `transform.parent` 的子节点 ——
也就是物品块 `_itemsRoot` 下的**兄弟节点**。这是必须的：

> 光晕要垫在物品块**下层**（中心被物品盖住，只露外圈），
> 而 uGUI 里子节点永远画在父节点自己的 Graphic **之上** ——
> 所以它不能当子节点。

代价是：`InventoryGridView.Refresh()` 里回收池化节点的那句

```csharp
if (_pool[i].gameObject.activeSelf) _pool[i].gameObject.SetActive(false);
```

**只关掉物品块自己**，兄弟节点光晕照旧显示在最后一帧的位置 → 卡死。
触发条件正好是"揭晓动画那 0.18 秒内把物品捡走"（狂按 F 就会撞上）。

**修法**：`ItemCellView.OnDisable()` → `StopRevealEffects()`。
所有"节点被回收/界面被关"的路径最终都走 `SetActive(false)`，钩在 `OnDisable` 上就不会漏。
（不在 `Refresh()` 里逐个调，是因为回收路径不止这一处，漏一处就是这个 bug 复发。）

### ② 光晕形状跟住物品轮廓（设计变更）

**原先不是**：光晕是**边长 = 物品短边**的正方形。
所以 1×1 看着对（正方形正好），2×4 只得到 2×2 的方光，上下边缘根本没被光包住。

这是 21.12 那一轮"圆形改方形"时留下的简化 —— 当时只验证了 1×1 的物品。

**现在**：`GlowGraphic` 拆成「核 + 外扩带」两个概念。

| 概念 | 含义 | 谁决定 |
|---|---|---|
| **核** `coreSize` | 物品真实占位（像素），带内 alpha 恒 1 | `ItemCellView` 用 `_rt.sizeDelta` 传入（含 1.5px 内缩，正好贴合看得见的那块） |
| **外扩带** `margin` | 核到 quad 边缘那一圈，**两轴等宽** | 动画：`-0.025 → 0.55 × 物品短边`（见下方调参记录） |
| quad 尺寸 | `core + 2 × margin` | 上面两者相加 |

于是 2×4 的物品得到 2×4 的核 + 四周等宽的光，1×4 也不会变成奇怪的椭圆。

**换算说明**：旧版是"短边正方形 × 0.95 → 2.4 倍"，等价于带宽
`(0.95-1)/2 = -0.025` → `(2.4-1)/2 = 0.70` 倍短边。

**调参记录**：矩形化时先沿用 0.70（保证 1×1 观感不变），用户实测
*"再把光晕范围再调小一点点，现在有点太大了"* → 改为 **0.55**。
外扩半径缩到约 79%，而 alpha 尾段按 `t²` 淡出，所以真正能看见的那圈光
缩小约 1/3（最占地方的就是淡到几乎看不见的外围雾）。
今后要再调，只改 `ItemCellView.GlowMarginEnd` 一个常数即可。

**顶点采样为什么不能用均匀网格（这条值得记下来）**：
衰减只发生在 `margin` 那条**窄带**里。均匀网格下，1×4 物品的 quad 高 250px、带宽只有 30px
→ 带内可能一个采样点都没有 → 光晕退化成**硬边方块**。
所以 `AxisSamples` 每个轴单独生成坐标：**带内 4 档（0/0.33/0.66/1）+ 核内 3 档**，
核内那几档 alpha 恒 1（反正被物品盖住），带内那几档保证不管物品多长都平滑。
11×11 = 121 顶点，一次重建成本可忽略。

**alpha 的定义**：`d = max(|px| - coreHalf.x, |py| - coreHalf.y)`（到**核边框**的切比雪夫距离，
核内为负 → alpha 饱和为 1），再 `t = d / margin`，`a = clamp01((1-t)/(1-solid))²`。
用切比雪夫而不是曼哈顿：后者会得到菱形光晕。

### 附：`Importer(NativeFormatImporter) generated inconsistent result` 警告

用户同时报了这条：

```
Importer(NativeFormatImporter) generated inconsistent result for asset
(guid:0c339de80c23c9b4b91d7963dfcf35ad) "Assets/Art/Fonts/NotoSansSC/NotoSansSC-Light SDF.asset"
TMPro.TMP_EditorResourceManager:DoPostRenderUpdates()
```

**结论：无害，资产没有损坏**。依据：

1. **GUID 不冲突** —— 全工程只有 `NotoSansSC-Light SDF.asset.meta` 一处含这个 guid
   （"inconsistent result" 最常见的真因是两份 .meta 撞 GUID，这里排除）
2. **文件内容没变** —— 报警告时该 .asset 的 mtime 确实被刷新了（13:37:47），
   但 `git status` 完全干净 → TMP 回写的结果与磁盘上原有内容**字节一致**

**机制**：TMP 的动态字体在编辑器里会把"本次运行新光栅化的字形"回写进字体资产
（`DoPostRenderUpdates` 走 `EditorApplication.delayCall` → 保存 → **强制重新导入**）。
既然保存和重新导入是同一个回调里连着做的，Unity 的原生资产导入器就会看到
"文件在我导入的过程中被改过" → 报 inconsistent result。
中文是动态字形，新会话里第一次渲染某些汉字时必然触发一次。

**什么时候才需要处理**：如果它**每次都刷**、而且那个 .asset 在 git 里**反复变脏**，
说明字形在无限增长 → 那时再考虑用 `Window > TextMeshPro > Font Asset Creator`
烘焙一份**静态** atlas（需要先确定字符集，对中文不划算，所以现在不做）。

### 复测清单（给用户）

1. 搜出**一件 2×4 或 1×4 的物品** → 光晕应该是**长条形**（跟住物品轮廓），不是正方形
2. 搜出 1×1 物品 → 观感应与之前**一致**（正方形，起始略藏在物品下）

4. 连按 F 捡完一箱 → 关门/关界面后不应残留任何光斑
