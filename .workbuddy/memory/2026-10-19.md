## 🎯 白字无描边根因（04:56）：IMGUI 的 hover 状态

- 修复：新增 `SetTextColor()` 一次性设置 normal/hover/active/focused/onNormal/onHover/onActive/onFocused；`AmmoHud` 同样修复（同类隐患）
- 经验：**用 OnGUI 画文字必须把 8 个 GUIStyleState 全设一遍**，只设 normal 会在鼠标悬停时被默认皮肤覆盖

## 讨论：联网自动更新系统可行性（10:55，只讨论未动手）

用户问"给游戏加自动检测/下载/安装更新，难度多高"。结论：

- **难度取决于更新对象**：数值配置（JSON/配置表）★☆；资源（Addressables）★★★；**C# 代码默认不可热更**（IL2CPP 编译进包，改一行也要重打包），需 HybridCLR ★★★★★
- **硬约束**：Windows 不允许替换正在运行的文件 → 更新必须由**独立启动器进程**在游戏未运行时执行；流程 = 拉 manifest → 下载到临时目录 → 校验 hash → 原子替换 → 启动游戏 → 失败可回滚
- **四条路线**：A 平台代劳（Steam 差分更新 / itch.io butler）最省事；B 自制 Launcher + 整包 zip（1~2 周）；C Addressables 资源热更（需早期规划，retro-fit 极痛，现在阶段 5 改还来得及）；D HybridCLR 代码热更（数周，架构级）
- **被低估的成本**：CDN 带宽（1GB × 1000 次下载 ≈ 1TB 流量）、UAC 权限（别装 Program Files）、断电/断网导致半残版本、HTTPS + 签名（否则被劫持下发木马）、跨版本升级测试矩阵
- **给本项目的建议**：阶段 5 不做。只留两条零成本缝 —— ① 版本号单一来源；② 数值走配置（§3.6 已规划）。真要做时顺序：先上平台（A），其次自制 Launcher 全量 zip（B，别一上来做差分），Addressables / HybridCLR 暂缓
- 判断前提：更新系统的价值 ∝ 更新频率 × 玩家数。少量玩家低频更新 → 网盘分发足够

### 后续（11:02）：用户确认分发走 Steam

- **Steam 路线确定**：更新无需自写代码，SteamPipe 自动做 chunk 级差分；用 beta 分支做测试发布
- 补充说明「游戏开着也能更新」的四种真相：① Steam 只是下到暂存区，退出后才应用；② 游戏内置下载器下到缓存目录（Warframe/命运2），重启生效；③ 脚本/配置热重载，立即生效（换的是数据和脚本，不是编译产物）；④ 逻辑在服务器，客户端零改动立即生效
- **能"云更新"的本质 = 这部分逻辑本来就不在客户端编译产物里**（在脚本里 / 在服务器 / 在数据里）。这是架构决策，事后补不上
